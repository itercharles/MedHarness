# MedHarness：定位、缺口、推广与实施计划（2026-11-14）

本文是一份交接文档。第 1–4 节是分析和决定，第 5 节是可以直接交给便宜模型执行的任务包。
状态基线：`main` 为 0.81.0；工作区里有五篇文档的压缩改动未提交（见任务 T0）。

## 1. 定位和核心痛点

**一句话（中文）：**
AI 写医疗软件很快，但每次变更都要留下设计控制证据。MedHarness 让 AI 同时写代码和证据，再用普通代码在合并前检查两者是否一致，对不上就不让合并。

**两句话（英文，用于 README、PyPI、GitHub 仓库简介）：**
> AI agents write medical-device software fast, but IEC 62304 wants design-control evidence for every change.
> MedHarness has the agent write that evidence with the code, and blocks the merge when ordinary code finds the two disagree.

**短版（80 字符内，用于 PyPI `description` 和 GitHub About）：**
> Change-control gate for AI-written medical-device software (IEC 62304)

**定位：** 它不是质量管理系统，也不是需求管理工具。它是 git 和 CI 里的一道关卡，
只回答一个问题：这次变更声称的影响，和分支上实际做的事，是否一致、是否完整。

**用户：** 1–10 人、用 AI 编程助手、没有专职质量/法规人员的医疗软件团队。
**证据的读者：** 审核员和公告机构。

**和替代方案的区别（推广时只讲这三点）：**

| 替代方案 | 问题 | MedHarness |
|---|---|---|
| 事后人工补文档（Word/Excel） | 慢，和代码对不上 | 证据和代码在同一个分支、同一次评审里 |
| 让 AI 直接生成文档 | 没人能确定完整、真实 | 由普通代码检查，不由模型检查 |
| 需求管理系统（Jira/Polarion 等） | 不知道代码改了什么 | 比较 CR 的声明和分支的实际改动 |

## 2. 现状：已经具备的

- 核心检查可用：`verify dhf`、`verify impact`、`verify tests`、`verify soup`，每条失败都给出条目、字段和修复命令。
- 发布证据一条命令生成：规格、追溯报告、测试证据、BOM、CycloneDX SBOM、哈希清单、签名审批单。
- 工具自身有验证：`build validation` 在用户环境里跑内置验证集并出报告；遗漏注入实验已有（`tests/integration/test_seeded_omissions_are_stopped.py`）。
- 新用户照 README 能装上、`init`、跑通检查（2026-11-14 在干净环境用 PyPI 0.81.0 验证过）。

**重排的理由：**
- **N1 提前到第 3 位。** 它本身不大，但 R2b 完全依赖按规范积累的历史：规范晚一天定，可用的历史就少一天。它还会改 CI 配方，所以要排在 T4 和 T7 之前。
- **T8 仍是内容上的第一位。** 它回答用户的第一个问题，不依赖任何东西，且全是文档和一个生成脚本。T0 排在它前面只是为了避免文档冲突；若发版未获同意，T8 可以直接在本地改动之上做。
- **R2 在 R2b 之前。** R2 是静态分析，范围清楚；R2b 噪声多、设计难，而且其中一个用途建立在 R2 之上。
- **T4 降为按需。** 目前没有已知的 GitLab 用户，配方又无法在本地验证；有人要时再做。
- **接口不考虑兼容（负责人决定）。** 目前没有真实用户，想改的趁早改；冻结只是对外推广的前置条件。
- **模拟审核最先启动。** 它不依赖任何工程项，而等待时间最长。

**R2 的范围决定（2026-11-14）：**
- 做：静态的盲区报告。关卡是确定性的，某个遗漏拦不拦得住可以从追溯图和配置直接算出，不需要真去注入。
- 暂不做：在用户的 CR 分支上真实注入遗漏再跑关卡。信息量与静态报告基本重合，“关卡代码对不对”已由 `build validation` 回答，实现复杂。有用户明确要求“眼见为实”时再考虑。
- 解决不了、要写进 `docs/trust.md`：漏建的链接。两个条目实际相关但没有链接，任何以现有图为准的检查都看不到，仍靠评审人。文字相似度之类的启发式提示会有误报，第一版不做。
- R2 改的是高风险关卡 `verify dhf` 的行为，要改对应需求条目和测试；先设计、评估，再实施，不交给便宜模型。

**R2b 的范围决定（2026-11-14）：**
- 用途按风险从低到高：`build plan` 的上下文输入 → `verify impact` 的警告 → 为没有模块归属的文件建议 `paths`（降低 R2 盲区的修复成本）。从第一项开始。
- 先不拦截。“一起改过”不等于“有依赖”：大范围格式化或重构、过时的关联、文件改名、新项目没有历史，都会产生噪声。用一段时间看准确度后再决定。
- 方向上的倾向：不存索引，每次从 git 历史算；不在代码里加需求标注；测试上已有的 `dhf_links` 一并用作代码到需求的追溯。
- **提交规范（负责人决定，2026-11-14）：每个影响 DHF 的 PR 都要写明属于哪个 CR。** 这回答了“哪次提交属于哪个 CR”。
  设计时要处理：PR 描述不在 git 里，而检查只读本机仓库、不读 GitHub，所以 CR 编号要落进 git。
  倾向：规范写“PR 标题以 CR 编号开头”，压缩合并后成为提交信息；工具做追溯时以分支对 CR 条目文件的改动为准，提交信息作补充，不依赖人是否守规范。
- 这条规范牵涉的现有内容：`init` 写进 `AGENTS.md` 的指引要加上它；CI 配方的 `change-check` 现在跳过分支名不带 CR 编号的 PR，
  按规范，改了 DHF 却不属于任何 CR 的 PR 应当失败（发布作业为 REL 条目开的 PR 等例外，设计时列清）。
- 属于核心的影响分析能力，先设计、评估，再实施，不交给便宜模型。

## 4. 推广和接入

### 4.1 接入公司流程：四级台阶

每一级单独有用，可以停在任何一级。推广材料和文档都按这个顺序讲。

| 级 | 做什么 | 成本 | 公司得到什么 |
|---|---|---|---|
| 0 试用 | 跟着教程走 10 分钟（T2） | 一个人，10 分钟 | 亲眼看到一次拦截 |
| 1 只加关卡 | 导入现有需求（T3），CI 里加 `verify dhf` | 半天到几天，取决于需求数量 | 追溯断链在合并前被拦住 |
| 2 变更走 CR | 分支命名 `develop/CR-NNN`，CI 加 `change-check`；AI 助手按 `AGENTS.md` 走 | 改团队习惯 | 每次变更的影响分析被代码检查 |
| 3 发布和签名 | `build release`、`item approve`、`build validation` | 配置签名人；跑一次验证 | 审核用的整套发布证据 |

**和公司现有质量体系的关系：** MedHarness 产出记录，记录归档到公司现有的质量体系里；
公司的软件变更 SOP 里加一段引用它（T5 提供模板段落）。它不替代 SOP、CAPA 或培训。

### 4.2 推广方案

目标是让对的人在 30 秒内判断“这和我有关”，10 分钟内看到效果。

1. **统一口径。** README 首屏、PyPI、GitHub About 用第 1 节的同一句话（T1）。
2. **一个可看的演示。** 教程（T2）录成终端录屏，放 README 首屏下方。录屏由负责人做，脚本就是教程里的命令。
3. **一篇文章。** 题目建议：“让 AI 写医疗软件，证据怎么办”。内容就是 README 的“问题”和“拦住什么”，加教程链接。由负责人署名发布。
4. **投放位置（负责人选择并亲自发）：** 医疗器械软件和法规从业者聚集的社区和职业社交平台、AI 编程助手的用户社区、开源项目展示渠道。发帖是对外行为，不交给模型。
5. **范例项目。** ContourLab 升级到当前版本后（T7），在 README 里作为“完整例子”链接到它的 DHF 和 CI。
6. **可信度。** 模拟审核有结果后（G7），把结论写进 README 的一行。没有结果之前不写任何“已通过审核”之类的话。

## 5. 实施任务包（交给便宜模型）

### 所有任务共同的规则

- 开工前读 `CLAUDE.md`、`docs/charter.md`。遵守其中全部规则，尤其是：文档和代码一起改；
  改了命令或返回内容要运行 `.venv/bin/python scripts/generate_interface.py`；行为变化要有接口层测试。
- 测试命令：`.venv/bin/pytest dhfkit/tests/ tests/ -q -n auto`。运行前把被 git 忽略的 `build/` 目录临时移走，跑完移回。
- 文档写给人读：短，按读者做事的顺序写；细节留给代码和 `interface.md`。不要加长已压缩的文档。
- **只在本地工作。** 不推送、不提 PR、不打 tag、不发版，除非负责人明确要求。
- 不要动 ContourLab 的仓库，不要通知它的会话。
- 每个任务做完，报告：改了哪些文件、测试结果原文、哪些没验证。测试失败就如实说。
- 遇到本文没覆盖的设计选择，停下来问，不要自己发明选项或字段。

### T8 “能信到什么程度”（内容上最优先）

事实基线（2026-11-14 运行 `tests/integration/test_seeded_omissions_are_stopped.py`：10 passed, 3 xfailed）：
诚实的变更通过全部关卡；12 种遗漏拦住 9 种（`medharness/validation/seeded.py` 的 `STOPPED` 八项，加“改了的需求丢了测试”）。
没拦住的三种：测试点没跟着改（只警告）、没有链接的新危害、验证用的测试被削弱。

- 新文件 `docs/trust.md`，不超过 70 行，三节：
  1. **检查保证什么。** 检查是普通代码，不是模型：同样输入同样结果。列出 `verify impact`、`verify tests` 各自比较什么。
  2. **拦截表。** 每种遗漏一行：拦住它的关卡，或“未拦住”及原因。表格由脚本从 `seeded.STOPPED` 和测试里的 xfail 清单生成
     （放进 `scripts/generate_interface.py` 的同类机制或新脚本），加守卫测试：文档里的表和清单不一致就失败。
  3. **检查不保证什么，评审人每个 CR 要看什么。** “已复审、无需改”的结论是否成立；追溯链接是否完整（没有链接的关系检查看不到）；
     测试是否真的验证了需求；是否有新危害。写成一份 4–5 条的评审清单。
- `README.md` 在 “What it catches” 之后加一节 “How far to trust it”，不超过 8 行：AI 的分析不被信任、由代码检查；
  拦住 9/12 及三个漏项各一句；链接到 `docs/trust.md` 和 `adopting.md#validating-your-installation`。
- `docs/reviews/charter-iterations.md` 不改（那是历史记录）。
- 口径约束：任何文档和推广材料不得写“保证完整”“确保正确”。只说：代码能查的由代码查，查不了的摆到评审人面前。
- 验收：守卫测试通过；数字出自生成脚本，不手写。内容须负责人审阅后合并。

**不在本任务内：** 用户项目的盲区报告见第 3.1 节 R2，待设计。`docs/trust.md` 里先用一句话说明：拦截能力取决于项目自己的追溯链接和模块代码归属。

### T2 十分钟教程

**第一步：先手工走通，不写文档（关口）。**
- 在临时项目里执行：`pip install` → `git init` + `medharness init` + 首次提交 → 建分支 `develop/CR-002` →
  `item create --type CR` → 用 `item update` 改 `SRS-001` 的一个字段 →
  `verify impact --cr CR-002 --since-ref main`（预期失败）→ 按失败信息里的 Fix 逐条修 → 再跑，直到通过。
  只用 `init` 生成的示例条目，不用 AI、不用网络、不用远端仓库。
- 约束：只用 `medharness item` 命令改条目，不直接编辑 `DHF/` 下的文件。填入的内容必须是这次改动的真实描述。
  如果发现空值或占位文字也能通过检查，把它作为发现报告出来：那是关卡的漏洞，不是捷径。
- 报告：每条命令和实际输出的关键一行；从第一次失败到通过用了几条修复命令、各修什么；哪几步的报错让人不知道下一步该做什么。
- **分流：** 修复命令不超过 6 条且每一步都能靠报错信息走下去，进入第二步。否则停下，把清单交给负责人，不写教程。
  手工路径是否太重由负责人判断，不要在教程里绕过。

**第二步：写教程和测试。**

- 测试：新增 `tests/integration/test_the_tutorial_runs.py`，按教程的命令序列在临时 git 仓库里执行，
