# Charter

> **Stability:** Draft
> **Last reviewed:** 2026-10-21

What MedHarness is for, and what it is not. Every proposed change is judged
against this page; a change that serves none of the promises below is not made.

## The problem

When AI agents develop software under IEC 62304, every change must leave
auditable design-control evidence. Today that evidence comes from one of two
places, and neither works:

- **Written by people, after the fact** — expensive, and it drifts from the code.
- **Generated by the agent along the way** — cheap, but nobody can be sure it is
  complete or true.

## What MedHarness is

A change-control gate that lives in git and CI. Every change request, from
opening to closing, produces DHF evidence that code can check; when the evidence
is missing or inconsistent, the change does not move forward.

## Who it is for

- Small medical-software teams (1–10 people) working with AI agents, with little
  QA/RA capacity.
- The people who consume the evidence: auditors and notified bodies.

## What it promises

1. **No drift.** The DHF and the code agree on the same branch, in the same review.
2. **Evidence as a by-product.** A release's traceability, specifications and SBOM
   are generated, not assembled by hand.
3. **An agent's change can be trusted.** Whether a change request's declared
   impact is complete can be checked — or at least challenged.

Promise 3 is the north star: it is the hard problem, and what sets MedHarness
apart. Promises 1 and 2 are the foundation it stands on and must not regress.

## What it does not do

- It is not an eQMS: no CAPA, training, suppliers or complaints.
- It does not judge whether a clinical or risk conclusion is right. It makes the
  judgment visible and open to challenge; it does not replace it.
- It has no requirements-editing UI.
- It does not try to cover every regulation. First, IEC 62304 and the part of
  ISO 14971 that a change touches.
- The features of the product it is tried on are not a goal: that product is a
  test bed.

## How we know it works

Each measure can fail:

- **Seeded omissions.** Change requests that deliberately leave out an affected
  item: the share that a gate stops.
- **Mock audit.** A 62304 auditor reviews the output of `build release`: zero
  findings on traceability or configuration management.
- **Overhead.** Compliance work per change request stays under a share of the
  total still to be set.

## Filter for new ideas

Before anything is built, ask: **does it make a change request's evidence more
complete, more trustworthy, or cheaper?** If none of the three, it is not built.

## Iterations

Each iteration answers one question, in this order:

1. **Inventory.** Map every existing capability to the promises above; cut or
   freeze what serves none.
2. **Completeness of impact.** Design the seeded-omission experiment, measure
   where things stand, then improve.
3. **Approval and accountability.** How a person's approval becomes a compliant
   review record.
4. **Tool validation.** MedHarness's own validation evidence.

What serves none of the promises:

- **The unattended CI runner** — `--pr` write-back and comments, session resume, the
  non-Claude model providers, and model-on-model design and code review. **Frozen**: it
  keeps working, gains no features. `--prompt` with the user's own agent covers the same
  ground, and a model reviewing a model is not a check made by code.
- **`verify soup` vulnerability scanning** (OSV) — cybersecurity evidence, outside the
  62304 and change-related 14971 scope. **Frozen**; extending it starts with this charter.
- **The `triage_result` gate** — it checks only that the model wrote `approved`, about
  its own work. **To be removed**, or folded into `impact_analysis`.

Gaps in promise 3, the input to iteration 2:

- **G1. Code changes do not reach the impact check.** It starts from the DHF items a
  branch changed; MODULE items name no code paths, and `verify changes --code-path` only
  asks that some file changed. A CR that changes dose calculation while declaring an
  unrelated SRS passes every gate.
- **G2. A new hazard has no way in.** Risk closure follows existing RCM links; a hazard
  linked to nothing is invisible. Code cannot find it, so it must be challenged: the
  `risk` dimension of `impact_analysis` has to carry evidence.
- **G3. Nothing is measured.** There is no seeded-omission fixture, so the share of
  omissions the gates stop is unknown.

Iteration 2 builds G3 first, measures, then closes G1 and shows the same fixture catch it.
